## 1. 结论

**当前版本不能据此宣告地形与性能验收通过。问题不是用户没有启用正确模式。**

| 问题 | 本轮结论 | 证据等级 |

| LEGACY 作为默认是否合理 | 当前实现没有足够依据把它作为新玩家默认，也不能把名字当作“完整保留原版行为”的保证 | 默认值明确存在；完整兼容性没有得到证明 |

应纠正此前的解释：UNIFORM 解决了适用城市域的统一高程，不等于已经解决整个生成组合的地形一致性；“非城市孔洞”只是描述位置，不能代替具体成因。高度图错误与实体断崖也是两个问题，不能承诺修好前者就自动消除后者。

## 4. 已确认：Minecraft 高度图与实体不一致

本节比较的是 Minecraft 区块 NBT 的 `Heightmaps.WORLD_SURFACE`，不是 TLC 的 `ChunkHeightmap` 标量，也不是 Citylines 的 `RawHeightSnapshot`。这三者不能混称。

逐列扫描所有已保存区段，仅排除 `air/cave_air/void_air`；树叶、草、地衣、水等全部计入最高非空气方块。NBT 按主世界最小 Y=-64、9 bit、每 long 7 项解码，并把“首个可用高度”减 1 转成最高占用 Y。目标块全部 256 列一致，亦验证了索引与高度约定。

| 区块 | 中心列真实最高非空气 Y | 高度图记录的最高 Y | 不一致列数 | 高估超过 16 格的列数 | 最大高估 |
|---|---:|---:|---:|---:|---:|
| `(11,43)` | 196，丛林树叶 | 196 | 0/256 | 0 | 0 |
| `(10,43)` | 99，草方块 | 166 | 256/256 | 252 | 73 |
| `(12,43)` | 100，草方块 | 166 | 256/256 | 254 | 79 |
| `(11,42)` | 150，草方块 | 181 | 182/256 | 164 | 71 |
| `(11,44)` | 80，草方块 | 126 | 251/256 | 249 | 70 |

例如西邻中心 Y=99 以上没有被漏算的树冠或屋顶，实际最高非空气就是草方块，高度图却仍认为顶面在 166。该误差不是植物过滤造成，也不是一格的编码偏差。

### 写回缺陷定位

参考源码 [ChunkDriver.actuallyGenerate](D:/Workspace/Citylines-forge-1.20.1/reference/lostcities-src/src/main/java/mcjty/lostcities/worldgen/ChunkDriver.java:42) 与当前 `run/.mixin.out/class` 导出的运行类均显示：

1. `SectionCache.generate` 直接调用 `LevelChunkSection.setBlockState` 写方块，绕过 `ChunkAccess` 的逐次高度图维护。对应源码第 464、479 行。
2. 写完后，在缓存给出的 Y 上，对四种高度图调用 `update(x,y,z,BEDROCK)`，见第 50..55 行。
3. Minecraft 1.20.1 的 `Heightmap.update` 不是“把这一列重设成此高度”。本轮对 Forge 47.4.0 实际映射 JAR 的字节码核验确认：低于现有顶面的实心方块更新不会降低旧顶面；降低需要旧顶面移除触发向下搜索，或者正确重建。
4. 当前运行类追加的 LC2H RETURN 钩子清理的是失效方块实体，不修复这些高度图。

因此，**这条削低地形后的高度图更新方法本身确有缺陷**，与本次大量“实际地形已低、高度图仍高”的现象一致。它是 TLC 写回路径中的问题，在当前整套组合中真实存在；不能因为位置在依赖内部就认为 Citylines 交付可以忽略。

证据边界：本轮没有生成阶段的逐次写入记录，不能证明每一个错误列最后都只经过这一条写入路径；也不能证明修复高度图就会移动已有石土体。错误高度图可能继续影响依赖区块高度的后续逻辑，但具体受影响消费者与影响量尚未测定。

## 5. 实体断崖：首要疑点是非城市整形路径不一致

### 已核实的执行分支

Citylines 的 [computeDecision](D:/Workspace/Citylines-forge-1.20.1/src/main/java/com/scarasol/citylines/terrain/TerrainFlattening.java:363) 先求城市因子，UNIFORM 对符合门槛的城市返回 G；非城市返回 `NO_DECISION`。后者表示 Citylines 不直接压平，**不表示后续没人再改地形**。

TLC 的 [doNormalChunk](D:/Workspace/Citylines-forge-1.20.1/reference/lostcities-src/src/main/java/mcjty/lostcities/worldgen/LostCityTerrainFeature.java:417) 在结构避让等条件允许时进入 `correctTerrainShape`。原生方法从四角约束网面插值得到逐列目标，再执行削填，见同文件第 590 行。

LC2H 的 `org.admany.lc2h.mixin.lostcities.worldgen.feature.MixinLostCityTerrainFeature` 在该方法入口接管。依赖 JAR 与当前合入后的运行类均核实了以下顺序：

1. `lc2h$preserveNaturalTerrain` 为真，取消原生整形。
2. 否则尝试 `TerrainCorrectionGpuPipeline.tryCorrect`，成功则由其接管。
3. 否则检查可选 `skipInteriorCorrection`，未取消才进入 TLC 原生整形。

第一步并非全区统一：除自然山地保护和城市混合开关外，还读取 `BuildingInfo`。直接结构避让、高速 X/Z 层级非负、X/Z 铁路走廊等会使它返回 false；读取异常也被捕获并返回 false。直接结构避让另受外层 `doNormalChunk` 条件限制，不能简单说“所有避让块一定被削平”。

这就允许相邻自然地形区块因角色不同，一个跳过后期削填，另一个继续进入削填；**该取消判定本身没有把两边的实际边界高度统一起来**。高速或地下铁路的角色也不要求地面出现一整块道路，不能凭地表没有马路就排除。

### 与本次样本的对应

`(11,43)` 保持高石土体且高度图自洽，四邻却普遍低很多并保留过高的高度记录。这与“部分区块经历后期大幅削低，目标块没有经历同等削低”的解释高度吻合。UNIFORM 把城市基准降到 71，可能放大仍进入城边整形的自然区块削填量，但没有同时证明 LC2H 保护跳过区块与这些削填区块能衔接。

JFR 在本次窗口确有 `correctTerrainShape`、`ChunkDriver.actuallyGenerate` 等调用样本，说明这些路径不是完全未运行；JFR 没有区块坐标，不能据此声称就是 `(11,43)` 或某个邻块。

另一个需要保留的候选是更早的密度位移：LC2H 的 `MixinBlenderCityEdge`、`MixinNoiseBasedChunkGeneratorTerrainGate` 与 `CityShiftField` 根据位移场准备状态、活动 Blender 和回退条件影响噪声填充。没有活动区域时可走原始路径，部分异常路径也会返回。**本轮没有证据证明目标块发生异步未就绪、吞异常或零位移回退，不能把“异步导致随机接缝”写成既定事实。**

### 当前能够下到哪一级结论

能够确定：城市统一面之外仍存在多套地形处理路径；当前样本在这些路径的职责交界出现严重实体接缝，同时伴有高度图写回错误。

最优先核对：目标及四邻实际是否分别命中自然保护、GPU/TLC 削填、密度位移回退，以及高速/铁路角色是否触发了差异。

尚不能确定：哪一条具体分支对这五个坐标承担最终责任，问题在不装 Citylines 的 TLC+LC2H 对照中是否同样出现，以及统一面相对原行为放大了多少。没有该对照，不能把责任全部推给 LC2H，也不能把所有问题都归给 Citylines 自身方法。

## 6. 最新火焰图：性能热点与结论边界

### 统计口径

读取最新 JFR 的 `jdk.ExecutionSample`，用 `jfr print --json --stack-depth 2048` 展开完整记录，实际最大栈深 306。全录制共 35,739 个样本。

主分析窗口是本地时间 **21:55:16（含）至 21:56:52（不含）**，覆盖世界初始化、生成/游览至离开，合计 **28,732** 个样本。JFR 对应 UTC 13:55:16..13:56:52。统计全部被采样线程，不把它称为纯区块生成基准测试；使用完整栈是为了避免深层调用被默认展示深度截断后漏计祖先方法。

| 链路/方法 | 命中样本 | 占窗口样本 | 含义 |
|---|---:|---:|---|
| Citylines `HeightField` | 0 | 0% | 未发现旧版高度场参与本轮热点；不等于其他成本为零 |
| Citylines `LevelFacts.rawHeight` | 0 | 0% | 自建高度场采样不构成本次已识别热点 |
| Citylines `road` 包 | 189 | 0.66% | 包含其下游调用；不是当前最大的可识别热点 |
| `iterateNoiseColumn` | 4,463 | 15.53% | 自然高度查询会实际执行噪声列计算 |
| LC2H `NaturalHeightSampler$LevelSampler.sample` | 3,804 | 13.24% | 与上一行、位移场行大量重叠，不可相加 |
| LC2H `CityShiftField` | 4,507 | 15.69% | 含自然高度采样、角色与区域准备 |

| Citylines `TerrainFlattening.withContext` | 7,223 | 25.14% | 包装方法的累计栈占比，不能当作它自己的 CPU 成本 |

自然高度采样的主要可见链路是：`CityShiftField` 角色/边缘高度请求 -> `NaturalHeightSampler` -> Minecraft 噪声列计算。在含 `iterateNoiseColumn` 的栈中，3,582 个样本含 `CityShiftField.roleHeight`，219 个含 `exactEdgeHeight`，621 个含 TLC `generateHeightmap`；这些仍是栈命中计数，不是调用次数或互斥账单。

最新日志第 218 行还记录了 21:56:26 的 `ChunkPostProcessor backlog ... 1024` 警告，说明后处理积压在 UNIFORM 下仍然出现。它不能单独证明哪一个生成方法导致积压，也不能直接等同于内存泄漏。

### 对性能问题的判断

1. “还在跑旧高度场所以慢”不符合本次证据。继续只优化那几处旧采样点，不对准这份录制的主要高度相关成本。
2. UNIFORM 取消的是 Citylines 选择目标平面的采样，不会自动关闭 LC2H 自身的山地混合、自然高度采样和位移场构建。此前不能把“目标高度不再采样”表述成整个组合都不再计算高度。
3. Citylines 也有真实的反向成本：[Lc2hCityHeightGateMixin](D:/Workspace/Citylines-forge-1.20.1/src/main/java/com/scarasol/citylines/mixin/lc2h/Lc2hCityHeightGateMixin.java:61) 在 UNIFORM 下强制两处高度资格门槛精确求值，使 LC2H 原本可能跳过的冷查询必须计算。方案已承认这种代价，但本次 JFR 不能直接分离它带来的净新增量；不能因此宣布 Citylines 没有额外成本。
4. 上表都是采样比例，不是帧率下降比例、总耗时增量或可直接相加的 CPU 账单。`withContext` 下面的原版/LC2H 工作不能全部归为包装函数自身开销。
5. 10,905 个样本栈顶为 `no_Java_frame`，另有 1,148 个 `unknown_Java`。存在明显的不可归因部分；当前录制也包含客户端、渲染与初始化，不能声称已经精确解释全部性能占用。
6. 旧 LEGACY 录制与本次录制的持续时间、游览和生成工作量不同，没有同坐标、同数量区块的 TLC+LC2H 对照。本轮不能给出可信的“慢了/快了 X%”，也不能判定“无明显新增开销”已经达标。

因此，性能诊断应从 **LC2H 位移场/高度采样及组合后的额外调用量、热路径回调与后处理积压** 着手，而不是先改三级道路参数或重新引入按城市 profile 定制的高度算法。

## 7. 对现有方案与默认行为的核阅结论

### 统一城市基准面并未被这次证据推翻，但接入不能算完成

用户这次观察到城内恢复正常，与 UNIFORM 的适用城市同高目标一致。非城市异常本身不证明需要放弃统一城市基准面或重新给城内分带。

问题在于，方案把非城市侧交给“当前生效的 TLC/LC2H 路径”，但保留这些路径不等于证明它们在新的城市基准下仍彼此协调。[通用城市高程方案 §5.1](<D:/Workspace/Knowledge Base/Lost Cities/路网优化方案/V3-拟真优先/通用城市高程-方案与共识.md:96>) 已描述保护跳过与整形接管，缺少的是这组实际组合的边界一致性证据，以及对方块写回和 Minecraft 高度图维护的检查。

这属于必须处理的兼容/完整性问题，不能用“地形功能在路网之外”来免责，也不需要借机扩成新的山区地形生成系统。用户接受城边断崖，不代表接受任意非城市块被孤立削低，也不代表接受错误的区块高度图。

### LEGACY 默认值是另一个明确的产品问题

[CitylinesConfig 第 83 行](D:/Workspace/Citylines-forge-1.20.1/src/main/java/com/scarasol/citylines/config/CitylinesConfig.java:83)仍将新配置默认设为 `LEGACY`；本地运行配置由用户改为 UNIFORM 并未改变这个代码默认值。

这里的 LEGACY 是此前 Citylines 的低频高度场路径，**不是“关闭 Citylines 并恢复原生 TLC”**。保留一条旧公式也不等于完整保留旧版本：共同 mixin、城市判定、依赖版本和后续生成路径均会参与最终结果，现有证据不足以保证与过去 100% 一样。

让首次安装的玩家默认进入不满足当前城内同高目标的路径，再要求其理解内部枚举、修改配置并重建世界，不是合理的默认体验。此前以“兼容”为这个默认值作笼统解释不成立，属于交付判断错误。已有世界的生成规则保护与新世界的默认选择应分开，不应把前者当作后者的理由。

本轮不擅自删除 LEGACY，也不更改默认值。此项不能掩盖更重要的事实：**只把默认切成 UNIFORM 也无法修复本报告中的非城市接缝。**
