# V3 实测三问题：诊断记录与修复思路

日期：2026-09-25。缘起：用户实机验收反馈三个问题——①建筑物直接阻断道路；②道路过于稀疏，几乎看不到；
③完全看不到主干道，只看到二级/三级。

**用户补充的关键事实（推翻了我的第一版推论）**：路是**被失落城市自己的建筑**截断的，
**周围没有原版结构**。因此"原版结构规避（`StructureAvoidance`）抹掉城市资格导致路消失"**不成立**，
该推论已作废，对应改动已回滚。

**盐策略**：用户确认**继续沿用盐 3**——本轮是修正与调参，不是重建逻辑。

---

## 1. 实测数据（可复现，探针在 `build/diag/`）

默认参数 `M=10 K=3 → S=30 区块 = 480 格`。

| 项 | 实测值 |
| --- | --- |
| 主干轴位置 | `x = n*30`、`z = n*30` 区块（每 480 格一条） |
| 集散轴 | 每方向**每超单元只有 1 条**（`offset=12`，即 `n*30+12`） |
| 120×120 抽象全城市同层窗口 | `P=6.6% / S=5.4% / T=3.2%`，合计 **15.2%**（与策划案记录的 15.0% 吻合） |
| `citylines.mixins.json` 加载 | 正常；`InjectionError`=0 |

**推论**：抽象条件下三级都存在且主干占比最高（6.6% > 5.4% > 3.2%）。
所以"看不到主干"**不是规划层没有主干**，而是主干在**生效链路**上被削减或渲染异常。

---

## 2. 已排除的两条假设

### 2.1 原版结构规避（`StructureAvoidance`）——**已排除**

`BuildingInfo.getChunkCharacteristicsLocked` 中 `avoidCity` 会把 `characteristics.isCity` 置 false，
而 `getEffectivePlannedRoadType` 在其**之后**执行，因此该格路类型会被 `resolve` 裁成 `NONE`，
随后单格建筑的 `plannedRoadType != NONE → b=false` 否决**失效**，建筑得以占用。

代码链条成立，但**用户实测周围没有原版结构**，故现实触发条件不满足。

> 我为此写的 `BuildingInfoStructureAvoidanceMixin` 注入**失败**（`No refMap loaded`，
> `@Local` sugar 在开发环境无 refMap 时不可用），且推论本身已被推翻，**已删除并回滚**。

### 2.2 多建筑否决路径缺失——**已排除**

`MultiChunkMixin`（M13，`canPlaceBuilding` HEAD）与 `BuildingInfoMixin`（M4，
`initMultiBuildingSection` RETURN）**都已接到** `V3RoadRights`，路径完整。

## 3. 剩余假设（需要运行时证据区分）

单格建筑能占用道路，唯一可能是该格的 `plannedRoadType` 解析为 `NONE`。而它解析为 NONE 只有三条路径：

| # | 路径 | 说明 | 可能性 |
| --- | --- | --- | --- |
| A | `!characteristics.isCity` | 该格不算城市 | 低（城市内部应为 true） |
| B | `!hasPlannedEdge` | **V3 的 `isReservedRoad` 要求"有等级**且**至少一条显式逻辑边"**。若某路格无边，V3 自己就认为它不是路 → 不占路权 → 建筑可占 | **中**（见 §4） |
| C | `overridden` | 预定义建筑/街道、或 `multiPos.isMulti()` | 低（多建筑路径已排除） |

另有一条**与路权无关、但会造成同样观感**的可能：

| # | 路径 | 说明 |
| --- | --- | --- |
| D | 多建筑占用**集散路/本地路** | `MultiBuildingStreetConflict.OVERRIDE_MINOR.roadBlocks` **只挡 PRIMARY**。M13/M4 已接 V3 路权，但**必须实测确认它们在 V3 维度真的被调用**（例如 `canPlaceBuilding` 是否真在跑、`isActive()` 是否为真） |

---

## 4. 我认为最可能的根因：**B（无边即非路）**

`V3RoadGraph.isReservedRoad` 复刻了 V2 的规则：

```java
roadType().isRoad() && cell.edgeMask() != 0
```

而 V3 连边要求**同层 + 可铺**（`V3Planner` L316/L361）。后果：

- **层高变化处断边**：相邻格 `cityLevel` 不等 → 无边 → 该格**不算路** → 路权消失 → 建筑可占；
- **城市掩码边缘断轴**：轴只在城市内铺，出城市即止 → 主干被切成短段 → 观感上"看不到主干"；
- 断掉的孤立格还会被 `dropIsolatedCells` **从计划里删除**，进一步减少可见道路。

**这一条同时解释问题 ①③，并与问题 ② 叠加**（15.2% 是抽象上限，真实世界因掩码+层高进一步削减）。

> 注意：策划案 §13 要求主干是"**跨多个规划单元的穿行骨架**；只在城市/同层可铺设分量边界或硬障碍处
> 合法终止"。所以"在城市内部因层高断掉"**不符合**策划案，属于缺陷而非设计。

## 5. 已加入的工具：`/citylines chunk [x z]`

为**不再靠猜**，新增区块级诊断命令（不带参数则用玩家所在区块）。它并排打印判定链的每一步：

```
chunk (x,z) MODE=V3
  plan: supercell=D[..] class=PRIMARY mask=0x5 transition=0x0 end=NONE
  plan reserves this chunk as a road: true   (needs a class AND at least one explicit logical edge)
  surface part: citylines:v2r_p_.... rot=0
  TLC: isCity=true rawRoad=PRIMARY effectiveRoad=PRIMARY couldHaveBuilding=false multiPos=SINGLE
  TLC: hasBuilding=false plannedRoadType=PRIMARY isPlannedRoad=true
  >>> road and Lost Cities agree: this chunk is a street
```

它对三种情况给出明确结论行：

- `>>> the plan gives this chunk a road class but NO explicit edge …`（**路径 B**）
- `>>> MISMATCH: the plan reserves a road here but Lost Cities resolved NONE (isCity=…, multiPos=…)`（**路径 A/C**）
- `>>> road and Lost Cities agree: this chunk is a street`（正常）

**如何在建筑压路的现场取证**：站到一栋"压在路上"的建筑旁，`/citylines chunk` 取该格；
再取相邻那几格。若建筑的格打印出 `effectiveRoad=NONE` 且 `plan class` 有等级但 `mask=0x0`，
即确认路径 B。

## 6. 修复思路（按优先级，等你取证后执行）

### P0 — 多建筑不得占用任何等级的道路（对应用户点 1）

不依赖 TLC 的 `OVERRIDE_MINOR`（它只挡 PRIMARY）。在 V3 路权层独立拒绝，
**不改 TLC 共享的 profile 实例**（与 V2 的 M13/M4 设计一致）。
**先验证** M13/M4 在 V3 维度确实被调用（可用 `debugLogging=true` 看 `multiCandidatesRefused`）。

### P1 — 主干必须跨单元连续（对应问题 ①③）

若取证确认是路径 B（层高断边）：

- 允许**同层容差**：主轴相邻格层高差 ≤1 时仍连边（坡道首版仍禁用，只连边不铺坡道）；
- 或让轴在城市内部**不因层高断开**，只在"可铺分量边界/硬障碍"终止——**这正是策划案 §13 的原文要求**。

**这会动到 `V3Planner`**。按用户指示盐仍沿用 3，但**这是算法行为变更**，
我建议先在抽象用例上量化"层高断边"的实际占比（无需改冻结代码即可测量），再决定改法。

### P2 — 稀疏（问题 ②）

`K=3`（480 格间距）是策划案选定的原型值，且明确"不因 TLC/V2 密度对照改动"。
但**前提是 P1 修好**——若主轴因断边损失大半，当前观感并不能代表 `K=3` 的真实密度。
**先修 P1，再评估是否需要调 K**；调 K 属于参数变更，按约束应走送审（`K` 是参与哈希的字段）。
