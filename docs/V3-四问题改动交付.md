## 2. D1 详述（已实现）

### 2.1 改动前的行为

`TlcRoadFacts.factsAt()`：

```java
boolean belowWaterLine = belowWaterLine(heightmap.getHeight(), waterLevel);
boolean water = LostCityTerrainFeature.isWaterBiome(provider, coord) || belowWaterLine;
```

含义：只要该格**城市生成之前**的天然地面低于水位线（或群系属于海洋/深洋/沙滩/河流），
就判为水格 → 计划不铺路 → TLC 因 `plannedRoadType=NONE` 正常放置建筑/公园 →
表现为"建筑压在路面上"、轴线被切 1~3 格（见问题描述 §2）。

### 2.2 改动后的行为

- 新增字段 `cityGroundLevel`（取自 profile，与 `BuildingInfo` L868-876 同源）。
- 新增两个纯函数：

```java
static boolean cityWater(int waterLevel, int groundLevel) {          // TLC doCityChunk L920-927
    return waterLevel > groundLevel;                                  // 只有全城淹水 profile 才为真
}

static boolean surfaceWater(boolean city, int waterLevel, int groundLevel, boolean belowWaterLine) {
    return city ? cityWater(waterLevel, groundLevel) : belowWaterLine; // 城外格保留天然水位线
}
```

- `factsAt()` 改为 `boolean water = surfaceWater(cityRaw, waterLevel, cityGroundLevel, belowWaterLine);`
- **`isWaterBiome` 不再单独定罪**（它是群系判定：被城市整平的沙滩/河岸仍是 dry 铺装地面）。
- **`belowWater` 原始事实保留**（桥扫描仍需要它）。
- 移除因此不再使用的 `LostCityTerrainFeature` import。

### 2.3 测试

`TlcV3FactSourceTest` 新增 3 条：

1. `cityChunkIsDryUnlessTheProfileIsDrowned`：城市格在天然地面低于水位线时仍是陆地；只有
   `waterLevel > groundLevel` 才算水；水位必须**严格高于**地面。
2. `outsideChunksKeepTheNaturalWaterLine`：城外格仍用天然水位线。
3. `dryCityChunkKeepsTheRawBelowWaterFact`：`belowWater=true` 且 `waterCell=false` 时，
   适配层仍发布 `land=true`（计划可铺）。

### 2.4 验证状态

- `tools/gradlew.sh build --offline` → **BUILD SUCCESSFUL，176 tests / 0 failures / 0 errors / 0 skipped**
  （原 173 + 新增 3）。
- 守卫：反射调用 0、真实 `@Redirect`/`@Overwrite` 0（5 处命中全在注释里）、mixin 配置 1 份、
  `V3Planner.java` 与 `V3Params.java` 未被改动（盐仍为 3）。
- **未验证**：游戏内观感。已生成区块不会改变，验收必须在新世界或未生成区域进行

## 3. D6/D7 详述（已实现）

### 3.1 设计落点

- **一个钩子**：`BuildingInfoCityLevelMixin` 用 `@WrapOperation` 抓 `BuildingInfo.getCityLevel`
  **内部**对私有 `getCityLevelLocked` 的那一次调用（`require = 1`）。
  - 为什么抓内部调用：这样 `original` 仍能取到**未经平衡的逐格层高**（地块平均需要它们），
    而所有走公开方法的调用方——建筑特征、多建筑足迹平均、`MultiChunk` 的铁路净空检查、
    我们自己的 fact 源——看到的都是同一个平衡值，正是 D7 要的"一个函数"。
  - 逐格层高缓存（`CITY_LEVEL_CACHE`）在 `getCityLevelLocked` 里，所以聚合地块**复用 LC 已算过的
    层高，不重复采样**。
  - `getCityLevelGui` 有意不拦：LC 的 GUI 预览继续显示未平衡的层高（已记录）。
- **纯函数** `BalancedCityLevels`：
  - 地块网格 `BLOCK = 10`，`origin(c) = floorDiv(c, 10) * 10`（与 LC 自己 `MultiChunk.getMultiCoord`
    的 `Math.floorDiv` 同原点，所以多建筑足迹不会跨地块）；
  - 取值顺序：① 地块被**主轴/集散轴**穿过时取**轴格层高的平均**（轴几何来自
    `V3Planner.axisTypeAt`，是坐标的纯函数）；② 否则取地块内**城市格层高的平均**；
    ③ 地块内没有城市格时**原样返回逐格层高**（荒野、高速、桥保持 LC 数据）；
  - 平均按 `int` 截断，与 LC 的多建筑足迹平均同一约定。
- **地块缓存**：`CitylinesRoadState.balancedBlocks`（`ConcurrentHashMap`，键=地块原点打包）。
  一个地块=100 格，第一次聚合后每格都是查表；值只依赖坐标/种子/profile，与生成顺序无关。
- **非 V3 维度不受影响**：`CitylinesRoadState` 不存在或未激活时直接返回原值。

### 3.2 静态校验（不依赖游戏）

用 `javap -c` 核对了 TLC 7.5.5 的编译产物：`getCityLevel` 体内确实存在且只存在一处

```
invokestatic  // Method getCityLevelLocked:(Lmcjty/lostcities/varia/ChunkCoord;Lmcjty/lostcities/worldgen/IDimensionInfo;)I
```

即 `@WrapOperation` 的目标描述符与调用点数都与实现一致（`require = 1` 成立）。

### 3.3 测试

`BalancedCityLevelsTest` 新增 7 条：地块网格的 `floorDiv` 与负坐标分块、同块同键、荒野保持原值、
城市格取平均、截断约定、轴格优先于城市格、同块任意格得到同一值、纯函数性。

### 3.4 游戏内实测（用户新世界 `新的世界 (1)`，2026-09-25）

用只读扫描（`build/scan2/blockscan.py`，以**路面材质**为地面标记）在 475 个有街面的区块、
48 个 10×10 地块上测得的相邻街面高度差：

| 相邻街面 | 有落差比例 | ≥12 格比例 | 最大落差 | 分布 |
| --- | --- | --- | --- | --- |
| **地块内** | **0.0%**（417/417） | 0% | 0 格 | `{0: 417}` |
| **跨地块边界** | 53.3% | 40.0% | 36 格 | `{0:14, 6:4, 12:5, 18:3, 24:2, 30:1, 36:1}` |

- **判定**：平衡按 D6/D7 生效——地块内绝对同高。剩余落差是地形本身：该城跨在山坡上，城市层高
  0→6 级（y=71→107，36 格），而平台只有 6 格一级，山坡上相邻平台必然差几级；平衡只改变落差的
  **位置与频次**（每 160 格一次，改前每 ~48 格一次）。
- **用户决定（D17）**：**暂不修复，仅记录。** 备选做法（D8 一级台阶交原版坡道、地块间落差上限、
  跨地块窗口平滑、更大地块、profile `useAvgHeightmap`）留档不实施。
- **顺带测量**：带本地路材质（`smooth_stone`）的区块 **13/475 = 2.7%**，至少有一条本地路的
  10×10 地块 **3/48 = 6.2%** —— 与抽象预测（本地路格占 3.65%）同向，本地路密度的去留另议。

### 3.5 未验证 / 已知影响（必须让审核看到）

- **游戏内未验证**：需要新世界或未生成区域；已生成区块不会改变。
- **性能增量未实测**：按纪律接入后跑固定种子 424242 的 2+2 次计时对照；仿真给出的新增挖填为
  1.5（丘陵）~6.7（断崖）格/列，且聚合复用已有层高缓存。
- **开关副作用**：`enableConnectedDistrict=false`（V3 未激活）的维度**不会**得到平衡高度，
  因此同一个世界在开关切换前后的**新生成区块**高度规则不同（老区块不受影响）。这是 D7
  "只对激活维度生效"的直接后果，记录在案。
- **地图集**：地块缓存随访问区块增长（每 100 区块一条），未做上限；量级可忽略，但未做驱逐。

## 4. D11 详述（已实现）

### 4.1 改动

- `V3Planner.throughAt()`：贯通式本地路的走线逐格补上

  ```java
  if (owner[at] != face.id || protectedParcel[at]
          || fact(x, z).cityLevel() != fact(ax, az).cityLevel()) return null;
  ```

  与 `spurAt`、`findDetour` 的同类检查一致。
- `V3Planner.edgeClasses()`：新增**生产守卫**——任何显式边若两端城市层高不同，直接抛
  `IllegalStateException("V3 edge crosses a city level at x,z")`，与既有的"边指向不存在的路"
  同一个风格，使这条不变量不可能被静默违反。

### 4.2 测试与**变异校验的诚实结果**

`V3EdgeLevelInvariantTest` 新增 4 条：均匀城市、地块内部"层高岛"、跨越地块的"层高分带"、
夹具自检。它们会遍历计划里**每一条显式边**并断言两端层高相同。

**变异校验（把修复临时去掉后重跑新测试）：新测试仍然通过。** 也就是说：
- 这 4 条测试**锁住了不变量**，但**没有复现出该缺陷的触发路径**（夹具没有让贯通线正好跨过
  层高岛：贯通线要同时满足"两端父路同层、整条线在面内、两侧邻格也在面内、且被
  `bestThrough` 选中"）；
- 真正兜底的是 `edgeClasses()` 的生产守卫；
- **未做到**：一个能在去掉修复后失败的定点夹具。已如实记录，留给审核决定是否值得补。

## 5. D12 详述（已实现）

### 5.1 改动

- `CitylinesRoadState.loadedFootprints(areaSize)`：从 `AssetRegistries.MULTI_BUILDINGS.getIterable()`
  读取**实际加载的**多建筑资产尺寸，去重、去掉超过 `areaSize` 的，得到足迹清单；
  `attach()` 在构造 state 时传入（此前是写死的 `(3×3, 2×2, 2×1)`）。
- `footprintsWithin(candidates, areaSize)`：纯过滤规则，负责去重与尺寸上限；资产为空或读取抛异常时
  记 `WARN` 并回落到写死的那三种形状（**宁可比实际多保护，也不能什么都不保护**）。
- 足迹清单照旧进入计划指纹（`V3Planner.fingerprint` 把每个 footprint 组合进哈希），
  这正是契约的要求："同种子、维度和足迹清单的策略变化必须再升版本盐，足迹清单也进入规划指纹"。

### 5.2 修复的缺口

契约「C 项收口：大足迹按需兜底」要求：普通 ≤3×3 地块在合并与本地路之前预留；**面积 ≥16 的
稀有足迹**在本地路铺完后按面积降序兜底（必要时撤销代价最小的整条本地路）。实现早已存在
（`preserveRareParcel()` 第一行即 `if (footprint.area() < 16) break;`），但清单写死为 ≤3×3，
**那条兜底永远不会触发**。现在玩家/数据包加入 7×7、9×9 资产后会自动生效。

### 5.3 测试

`CitylinesFootprintTest` 新增 5 条：大足迹（9×9、7×7）能通过过滤、超过地块尺寸的被丢弃、
同尺寸去重、小清单保持可用、全不可用时返回空（让调用方走回落）、空尺寸在构造期即被拒。

### 5.4 加载时序修复（游戏内日志暴露）

用户新世界的日志出现了本实现自己的告警：

```
[citylines] no multi-building asset is loaded; protecting the enumerated shapes so a datapack
cannot silently disable parcel protection
```

原因：`attach` 时 `AssetRegistries.load` 只填充 parts/buildings/stuff，**多建筑注册表要等有人第一次
请求才会加载**，于是 `getIterable()` 是空的，足迹清单回落到 ≤3×3——D12 想修的"稀有足迹兜底永不
触发"依旧存在。修法：`loadedFootprints(CommonLevelAccessor, int)` 先显式
`AssetRegistries.MULTI_BUILDINGS.loadAll(level)`（该方法是幂等的，会跳过已有名字）再读清单；
同时**启用行现在会打印实际足迹**：

```
[citylines] V3 planner enabled for minecraft:overworld (S=30, areaSize=10, footprints=3x3+2x2+2x1, fingerprint=...)
```

下次进世界的日志即可确认（基包没有 ≥4×4 资产，所以清单本就该是这三档；加载数据包后会自动变大）。

### 5.5 已知简化（记录，留给审核）

- 读的是**所有已加载**的多建筑资产，而不是"本维度城市样式能选到的那些"。原因：`WorldStyle`
  只暴露 `getRandomCityStyle(...)`，其城市样式选择器列表是私有的（`WorldStyleRE` 里才是公开的
  记录字段），要在不改 TLC 的前提下按样式收窄需要额外绕行。**代价**：数据包里存在但没有任何
  样式引用的超大资产也会被保护（本地路会因此少铺少量格）。若要收窄，需另找 style→selector 的
  公开路径，届时清单会变、指纹也会变。
- **未验证**：没有带 7×7/9×9 资产的世界，因此"兜底真的会撤销一条本地路"尚未在游戏内看到。

## 6. D4/D5 详述（已实现）

### 6.1 断面（`RoadSection` / `RoadType` 注释 / 生成器常量同步）

| 等级 | 断面（每 16 格 = 2×(步行+路缘) + 车行道） | 车行道材质 | 中线 |
| --- | --- | --- | --- |
| 主干 | 步行 1 / 路缘 1 / **车行道 12** | `gray_concrete`（P） | **有**，两格（第 7、8 格）`white_concrete`（C） |
| 次级 | 步行 2 / 路缘 1 / **车行道 10** | `gray_concrete`（P） | 无 |
| 本地 | 步行 4 / 路缘 1 / **车行道 6** | **`smooth_stone`（R）** | 无 |

- 三档车行道都是偶数且断面居中，**中缝恒为第 7、8 两格**，所以任何一段路的中心线都在同一条对齐线上。
- 本地路材质选 `smooth_stone` 是我的决定（用户授权"三级换一个浅色方块，你自己定"）：它与主干的
  `gray_concrete` 不同，也不与步行带的 `light_gray_concrete` 撞色；要换成 `light_gray_concrete` 只改一个字符。

### 6.2 中线规则（主干专属）

- **每条主干臂都画中线**（两格宽）——这是"共享边逐格一致"的要求：只在一侧画，接口会出现
  "一边有线一边没线"。
- **直行主干**（南北或东西贯通）：中线穿过整块，含中心方块。
- **四向皆主干的十字路口**：路口方块内不画线，只留四条臂的引线（与现实一致）。
- 只有一条主干臂（尽头）时，只画该臂的引线。

### 6.3 渲染角色与资产

- 新增角色 `LOCAL_CARRIAGEWAY`（本地车行道）与 `CENTRE`（中线），并新增 `isPaved(role)` 统一判定
  三种"行车面"；`RoadSurfaceHooks` 的"楼梯压路"判定改用 `isPaved`。
- 调色板 `v2_street.json` 增加 `C → white_concrete`、`R → smooth_stone`；受损调色板
  `v2_road_damage.json` 同步增加这两条（坏城时也会变旧）。受损字符必须在 LC 内置调色板里空闲，
  生成器自检强制这一点——我先试的 `{`/`}` 就被它挡下，最终用 `'` 与 `,`。
- 生成器写出的 38 个文件全部重生成（32 部件 + 桥面 + 2 调色板 + 3 样式）。

### 6.4 验证

- 生成器：`python3 tools/generate_v2_road_parts.py` → **self-check OK: 20,596 assertions，

## 7. D10/D13 详述（已实现）

### 7.1 机制

- `V3Planner.addLocalRoads` 保持原有"先收集面、每个面放一条本地路"的流程不变；放完一条后调用
  **新增的 `addExtraLocals(face, owner, faceId)`**：
  1. 把该面**仍然空着**、且不是受保护地块的格子"退回未归属"，用 `collectFace` **重新切分**——
     刚放的本地路和受保护地块天然成为边界；
  2. 每个重新切出的**闭合**子面只要仍达到 `extraLocalDepth`，就走与第一轮**完全相同**的选线逻辑
     （`bestThrough` → `bestSpur`），放一条本地路，然后递归到下一轮；
  3. ~~每个**原始面**最多 `localsPerFace` 条，递归自然终止。~~ **更正（2026-09-26 核阅第 2 项，未修）**：
     实现**没有**保证这条上限——`V3Planner.addExtraLocals` 把 `placed` 沿递归分支各自 +1，兄弟子面并不共享
     额度，所以一个原始面若在首条路后分出 k 个合格闭合子面，实际可放 `1 + k` 条。默认 `localsPerFace=2`
     变成"首条 + 每个子面各一条"。是否在默认地形里真的超过，需要先做抽象用例确认；修它会改变道路密度，
     属改方案，待决策。
- ~~**统计口径不变**~~ **更正（2026-09-26 核阅第 3 项，未修）**：`closedFaces` 仍只在初始收集时自增
  （`V3Planner:808`），但 `openFaces` 在初始收集（`:805`）**和**二次切分开放子面（`:873`）两处都自增，
  所以 `openFaces` 已经是"初始 + 二次"的混合口径，`closedFaces` 是初始口径，两者不可直接相除。
  `V3Planner:840-841` 的 javadoc"counters deliberately untouched"与 `:873` 自相矛盾。面面积 min/max 不受影响。
  只有 `throughRoads`/`spurRoads` 随实际铺设条数增长这一条仍然成立。
- **参数**（`V3Params`，进计划指纹）：`localsPerFace`（1..3，默认 2）、`extraLocalDepth`（≥`spurDepth`，
  默认 8）。**盐仍为 3**（决策已定：只修正、不重建），但指纹随参数变化——契约要求的"参数变则抽象
  证据重跑"已执行：`V3TopologyComparisonTest` 的默认行按新数字重新钉住，并**新增一条用例**用
  `localsPerFace=1` 复现改前的 1822/15.0%，旧证据仍可复现。

### 7.2 阈值是怎么定的（实测表）

## 8. 本地路稀疏：问题定位（仅汇报，未决策）

用户实机反馈"大部分街区没有三级路"。实测与定位如下。

### 8.1 实测（用户新世界 `新的世界 (1)`）

| 指标 | 数值 |
| --- | --- |
| 带本地路材质（`smooth_stone`）的区块 | 13 / 475 = 2.7% |
| 至少有一条本地路的 10×10 街区 | 3 / 48 = 6.2% |

### 8.2 判定本地路的四道门（`V3Planner.addLocalRoads`）

1. **面必须闭合**（`collectFace` → `face.closed`）：邻格若是**另一级的道路**、**不可铺**（水/障碍/城外）或触到超单元边界，面即判开放；`addLocalRoads` 对开放面**直接跳过**——该面一条本地路都不会有。
2. **深度**：`maxDepth ≥ throughDepth(6)` 才试贯通路，否则 `≥ spurDepth(3)` 才试支路；都不满足则不铺（无计数器）。
3. **要有可行走线**（`bestThrough`/`bestSpur`）：两端父路同级、整线同级（D11）、两侧可建设、不穿受保护地块；失败计入 `preRescueNoLocalRouteAreas`。
4. **第二条**（D10）：闭合面放过一条后重新切分，子面需 `maxDepth ≥ extraLocalDepth(8)`。

### 8.3 卡在哪道门：抽象实测（3 种子 × 3×3 超单元 = 243 个 10×10 街区）

| 场景 | 闭合面 | 开放面 | 铺出的本地路 | 够深但无线可走 | 含本地路的街区 |
| --- | --- | --- | --- | --- | --- |
| 开阔城（无障碍） | 87 | 0 | 104 | **0** | **57.6%** |
| 城中有 4×4 障碍 | 83 | 5 | 99 | 0 | 53.5% |
| 城中有水带 | 80 | 10 | 96 | 0 | 52.7% |
| 城跨两个层高 | 69 | 18 | 83 | 0 | 47.7% |
| 山坡城（每 10 格升一级） | 42 | 73 | 52 | 0 | 25.5% |
| **梯田城（每个街区边界换级）** | **18** | **92** | **23** | **0** | **9.1%** |

结论：
- **"够深但无线可走"始终为 0** ⇒ **深度阈值不是瓶颈**；开阔城里**每个闭合面都拿到了本地路**（104 ≥ 87，D10 允许一面两条）。
- **瓶颈是第 1 道门"面必须闭合"**：层变越多 → 开放面越多 → 本地路越少。把"每 10 格换一级"（正是平衡后山坡城的形态）代入，街区覆盖率 57.6% → **9.1%**，与用户实测 6.2% 吻合。

### 8.4 结构性补充

- 本地路的单位是**面**，面由轴线（每 30 区块的主轴/集散轴）围成，一个面约 30×30 区块（≈9 个 10×10 街区），一面通常 1~2 条 ⇒ 即便开阔城，"每条街都有本地路"也不是现行设计目标。
- 障碍/水会减少闭合面（5~10 个开放面），非主因；受保护地块未成为瓶颈（`noRoute=0`）。
- **同源**：D6 平衡把每个街区变成一块平台，山坡地形下相邻平台差 1~6 级 ⇒ 面频繁触碰"另一级的道路" ⇒ 判开放 ⇒ 不铺本地路。这与"地块边界落差"是**同一个原因**。

### 8.5 可动杠杆（备查，本轮不决策）

1. 让**层变不再使面开放**（面按层切成同级子面，各自判定闭合）——直击本因；
2. 减少层变数量（D17 已决定只记录的那几条：落差上限 / 跨地块平滑 / 更大地块 / 原版平均高度图）；
3. 允许开放面也铺本地路（改策划案第 29 行"不闭合则不铺"的语义）；
4. 调深度阈值（实测**几乎无效**，瓶颈不在这里）；
5. 改变本地路的"面"单位（例如以 10×10 街区为单元）——改动最大，需重新定义规则。

### 8.6 "三级路能不能跨街区 / 两个街区合并成一条路"的实测

**同级相邻街区：已经是合并的。** `collectFace` 在**同一层高**内会跨过 10×10 街区边界泛洪，
所以一个面本身就可以横跨多个街区，一条本地路服务它们（开阔抽象城里 57.6% 的街区含本地路，
而每条本地路长约 18~35 格）。

**不同层高的相邻街区：现在不行**，三个原因叠加：
1. 计划的连边一律要求两端同层（14 处判定，含本地路的三条路径）；
2. 面只要碰到**另一级的道路**就判开放 → 一条本地路都不铺；
3. LC 自己的坡道**一次只能爬一级**（`getStreetSlopeDirection` 要求邻格恰好 `cityLevel + 1`），
   差 2 级及以上的边界**没有任何过渡件**。

**两条让它"跨过去"的路线，及实测代价：**

- **(A) 允许本地路跨"一级"落差**（低的那格由原版自动生成坡道——LC 的坡道判定只看"是否同为干道级"，
  三级路同样适用）。适用条件：落差恰好 1 级。用户世界的边界落差里 **4/30 = 13% 是 6 格（1 级）**，
  其余 ≥2 级，救不了。
- **(B) 把"差不超过 N 级"的相邻平台合并成一个平台**（按合并后的平均高度整平，台阶消失）。
  用户世界 48 个街区的实测（只读扫描 + 归并仿真）：

  | 合并阈值 | 平台数 | 平台边界落差分布（格） |
  | --- | --- | --- |
  | 不合并（现状） | 28 | `{0:21, 6:20, 12:10, 18:6, 24:4, 30:2, 36:1}` |
  | ≤1 级 | **10** | `{0:43, 12:4, 18:3, 24:13, 36:1}` |
  | ≤2 级 | 7 | `{0:47, 18:3, 24:10, 30:4}` |
  | 全部合并 | 1 | `{0:64}` |

  平台越大，街区面越容易闭合、本地路越多（抽象实测，平台尺寸 → 含本地路的街区比例）：

  | 平台尺寸 | 闭合面 | 开放面 | 含本地路的街区 |
  | --- | --- | --- | --- |
  | 全平（一个平台） | 87 | 0 | **57.6%** |
  | 每 60 格（6 街区） | 69 | 18 | 49.4% |
  | 每 20 格（2 街区） | 66 | 33 | 45.7% |
  | 每 10 格（1 街区，现状） | 42 | 73 | 25.5% |
  | 每 5 格 | 30 | 88 | 17.3% |
  | 每边界换级（用户世界形态） | 18 | 92 | **9.1%**（实测 6.2%） |

  **代价**：合并**不消灭高度差**，只是把它集中到更少的边界上——剩下的台阶更大（12~36 格集中在
  少数边界，且 LC 没有多级坡道，那些地方仍是一堵墙）；挖填量随合并阈值上升。
  **收益**：平台变大 → 面更容易闭合 → 本地路覆盖率显著上升。

### 8.7 复现

`V3LocalRoadCoverageTest`（2 条用例）把 8.3 的两个事实钉成回归：开阔城里每个闭合面必有本地路；"梯田城"下开放面 >10×、闭合面 <1/4、街区覆盖率 <1/5。
