### 2.1 一处必须记录的修正：上下文要压在 `doFill`，不是 `fillFromNoise`

第一次实机计数器显示：填充阶段的 2,457,600 次覆盖调用**全部没有 frame**（`noframe 2457600 / consulted 0`）。
根因在 `NoiseBasedChunkGenerator.fillFromNoise` 自身（反编译 L259）：

```java
return CompletableFuture.supplyAsync(Util.wrapThreadWithTaskName("wgen_fill_noise",
        () -> this.doFill(...)), Util.backgroundExecutor()) ...
```

真正的逐格填充被丢到 `Util.backgroundExecutor()` 的**另一个线程**上执行，所以在 `fillFromNoise` HEAD 压的 ThreadLocal 不在填充线程上。
把注入点改到 `doFill`（`m_224284_`，同一个线程）后：`noframe 0 / consulted 2,457,600` ✓。

## 3. 行为要点

1. **只压 LC 判定的城市区块**（逐区块）：`City.getCityFactor(coord, provider, profile) > profile.CITY_THRESHOLD`，用**原始**高度评门槛。
2. **高度来自低频场**：格子 2048 格（128 区块，可配置）、**格内 5 点**（格心 + 四个四分点，吸附到区块中心）**只取海平面以上的样本**求中位数，相邻 **3×3 格**的中位数作为参考高度，**就近**量化到 `GROUNDLEVEL + 6k`（k clamp 0…8）。
3. **层高钩子让地面与地形逐格相等** ⇒ trim 恒 0、LC 城内整平空转，且**与任何 profile 的分带阈值无关**（不需要改数据）。
4. **四条守卫**：`LandscapeType != DEFAULT` 不压；**本格 5 点里不足 3 点为陆地则不压**（水格，准入只看本格，§5.5）；**参考高度** ≤ 海平面+1 不压；`G` 超出维度高度范围不压。掩码与采样一律用原始高度（采样模式）。
5. **只做空气 ↔ 固体转换，且只在地面以下**：**地面以下**的非空气方块（水、矿脉、深板岩）原样保留，只有空气会被填成默认固体 ⇒ **地面以下的水会留在城市地基里（空腔/暗河，尚未验收观感）**；**地面以上的任何方块（包括水面）都会被置为空气** ⇒ 城市格子里高于目标地面的水体（山间湖、河面）会被抹掉。"流体一律原样"只对地面以下成立（2026-09-26 核阅更正）。
6. 决策对每个区块只算一次并缓存（按维度），且只依赖 seed/维度/区块坐标 ⇒ 与区块生成顺序无关。
7. 诊断：`debugLogging=true` 时打印前 300 条决策（含拒绝原因）与每 500 个压平区块的进度。

### 4.1 探针方法上的两个坑（留给后续验证）

1. **`gradlew runServer` 不转发 stdin**：`forceload add …` 与 `stop` 这类控制台命令不会被执行（早先的 `sleep | runServer` 写法无效）。要按需生成指定区域，必须走 RCON。
2. **`timeout` 杀掉 gradle 不会杀掉它 fork 出来的服务端 JVM**：会占住 25565 端口，让下一次探针启动失败（本次踩到两次）。每次探针后要显式清理 `enabledGameTestNamespaces` 的服务端进程；另外杀过 gradle 守护进程后，下一次要加 `-Dnet.minecraftforge.gradle.check.certs=false`（离线环境下 forge gradle 的证书校验会失败）。

### 5.3 实机验收发现的设计缺陷与修复（2026-09-26 晚）

**症状**：用户新世界里城内高度差仍然明显。

**证据**：
- 用户客户端日志 `run/logs/2026-09-26-1.log.gz`：15:36 删旧世界、15:37 新建 `新的世界`（所以不是"已有存档不变"），15:37:10 打印 `terrain flattening enabled (cell=2048, smoothing=true, groundLevel=71)`，出生点道路 y=83（level 2）⇒ 功能确实被加载。
- 用**用户世界种子**（8218742260916520910）跑探针：**269/300 决策被拒**，绝大多数是 `cell median 65 <= sea 63 + 2`（还有 59/61/63/64），只有约 40 个被压平。
- 扫描用户新世界存档（只读）：274 个城市区块分布在 4 个 2048 格子里，**格内相邻城市区块 26.7% 有落差、24.0% ≥12 格、最大 24 格；跨格只有 5 对** ⇒ 落差发生在格子内部 ⇒ 那些区块根本没被压平，仍在用 LC 的 8 格分带（以及非压平区块的 D6/D7 平衡）。

**根因（本方案的实现缺陷，不是 D6/D7 遗留）**：水守卫的判据放在了 **2048 格中位数再经 3×3 格平滑**（覆盖约 6.4 km 区域）之上。用户的图是**山地海岸**（自然地表 48~175），城市所在格的中位数落在 63~65（贴着海平面），于是整格被拒；而城市本身的地面在 83~119。
（先前 §5.1 的 A/B 之所以"看起来正常"，是因为那块探针区域地势低、守卫恰好放行；此前 §5 的仿真用的是**区块级替代数据**、不是 9 点采样+3×3 平滑，所以没有预测到这次拒绝。）

**修复**：
1. 采样从 9 点（3×3）改为 **25 点（5×5）**；
2. 求中位数时**只统计海平面以上的采样点**（`> seaLevel + 1`），海/河/低地样本直接丢弃；
3. 陆地样本不足 **6** 个才拒绝整格（"水格"判据从"中位数低于水位"改成"陆地样本太少"）；
4. 规则抽到纯类 `FlatteningMath.landMedian(...)` 并加 2 项单测（山脉城市不被水面拉低、水域格被拒）。

**状态**：修复已写入源码，但**尚未构建/实机验证**——工作区当前因并行的 V3 桥接开发（`road/core/` 新增 5 个文件 + `CitylinesRoadState` +81 行缺 import）编译不过，不触碰他人改动。

**工具**：`gradlew clean` 会删除 `build/scan2/` 下的旧分析脚本，因此把世界扫描器重建为
**`tools/analysis/scan_world.py`**（自包含、只读）。它同时修正了旧脚本的一个缺陷：旧判据"顶面 ≥60%
落在 71+6k 网格"会把**平坦自然台地**（高度恰好网格对齐时命中率 100%）误判成城市，从而造出
"幽灵城内台阶"；新工具**只认街道材质**。性能对比用 **`tools/analysis/jfr_report.py`**（自包含、只读：
传 `jfr print --events jdk.ExecutionSample --stack-depth 48 <快照>.jfr` 的输出到 stdin；可选第一个参数是
"只统计匹配该正则的栈"的**范围过滤**，本轮的"区块生成栈内占比"即由此得到）。

**本轮未做到 / 未验证**：

1. **性能复测的剩余缺口**：整模组占用已复测（见上：20:18 快照，区块生成栈内 49.55% → 6.40%，
   `rawHeight` ≈100 倍），但仍未做到：
   **同场景严格 A/B**（两次录像时长/负载不同，只能比栈内占比与每秒速率）、**延迟与锁**（JFR 只做 CPU
   归因；修-3a 复用的 LC 高度图带 `synchronized(this)`，是否在同一维度内形成竞争仍未测）、以及
   "每次决策整列求值 225 → 45 次"的**逐调用计数**（现仅有按帧的总量归因）。
2. 与 25 点 oracle 的**同区块** level 直方图对比**未做**（两次探针的 debug 预算覆盖了不同区块集合）；
3. 与 oracle 的**偏差分布**未做；
4. 验收区域偏小（14 个街道区块 / 1 个格）——足以确认"格内同高"，不足以做统计外推；
5. `docs/地形压平-性能修复-策划案.md` §5 里提到的"守卫组合真值表"以**纯函数单测**形式落地（`FlatteningMath.groundFor`），而"掩码顺序对结果无影响"由该单测的对称性断言 + 本次种子复算共同支撑。

## 5.5 核阅发现的守卫缺陷与修复（2026-09-26 晚，经授权实施）

**来源**：`docs/2026-09-26-改动核阅问题.md` 第 1 项（高）。核阅为静态控制流分析，我已逐行复核并确认。

**缺陷**：`HeightField.computeTargetLevel` 只检查 `smoothedMedian` 的返回值，而平滑会**丢掉所有没有值的邻格**（`HeightField.smoothedMedian`）。于是**目标格自己 5 点里不足 3 个陆地点**（本格 `cellMedian → NO_HEIGHT`）时，只要 3×3 里有一个陆格，本格就拿到 level 并进入压平 ⇒ **水格准入被邻格绕过，恰好发生在海岸线与河岸**（守卫最该生效的地方），与 §5.4 自己写的"陆地样本不足 3 个则整格被拒"不符。

**修复（准入与参考分离）**：

| 项 | 内容 | 落点 |
|---|---|---|
| 准入 | 只看**本格自己**的 5 点：`cellMedian(cellX,cellZ) == NO_HEIGHT`（陆地样本 < 3）⇒ 直接 `NO_LEVEL` | `HeightField.computeTargetLevel` |
| 参考 | 通过准入后，高度仍取 3×3 格平滑中位数；`isWaterCell(平滑值, sea, +1)` 继续生效 | 同上 |
| 接缝 | 规则抽成纯函数 `FlatteningMath.cellTargetLevel(ownMedian, smoothedMedian, sea, margin, groundBase)`，可单测 | `FlatteningMath` |
| 单测 | 新增 2 项：**本格无值 + 邻格陆地 → 拒绝**（核阅点名要的回归用例）、**参考值 ≤ 海平面+1 → 拒绝** | `FlatteningMathTest` |

副作用：`HeightField.NO_HEIGHT` 改为 `FlatteningMath.NO_LAND` 的别名（同一 `Integer.MIN_VALUE`，避免两处哨兵各写一遍）；本格中位数为缓存命中，准入判定**不新增任何采样开销**。

**复验（2026-09-27 01:0x 服务端探针，同种子 8218742260916520910、同协议、debugLogging=true）——结果推翻了我原先"严格收窄、不影响原有陆地格"的判断**：

三次探针的决策窗口（调试预算 300 条）逐行分类，同一决策顺序、同一种子：

| 探针 | 构建 | FLATTENED | 城市区块被拒（cell level −1） | 非城市被拒 | 出生点格 (−1,0) |
|---|---|---|---|---|---|
| 16:17 | 25 点（§5.3） | 268 | 0 | 0 | 区块 −10,0 → level 1（ground 77，median 78） |
| 17:18 | 5 点（§5.4，**修复前**） | 216 | **0** | 67 | 区块 −10,0 → **level 0（ground 71）** |
| 01:0x | 5 点 + 本格准入（§5.5） | **66** | **150** | 67 | 区块 −18…−24,3 → **不压平** |

⇒ 本格准入把窗口内 **150/216 = 69%** 的城市区块压平决策改为拒绝；整轮的 `flattened so far` 计数也从"Done 前已过 1000"降到"Done 时不足 1000"。

**因果是确定的，不是猜测**：同一粒子的同一采样点、同一陆地阈值（> sea+1）、同一 `smoothedMedian` 与同一 `isWaterCell` 在两次构建里完全一致；17:18 构建对该格给出 level 0 说明平滑值 ∈ [68,74]、水守卫通过，因此本次拒绝**只可能**来自新增的"本格 5 点不足 3 点为陆地"。即：出生点城市所在格 (−1,0) 自己的 5 个采样点里 ≤2 个高于 y=64，按 **D-T8 的字面规则它是"水格"，不许压平**。

**世界扫描（修复后探针世界 `run/flattenprobe5`）**：

```
city-like chunks: 13
  cell (-1, 0): 12 chunks, levels {2: 2, 3: 7, 6: 3} -> grounds [83, 89, 107]
  cell ( 0, 0):  1 chunks, levels {0: 1}            -> grounds [71]
同格内相邻城市区块: pairs 9 | 有落差 0.0% | >=12格 0.0% | max 0
```

⇒ 出生点城市（自然地形 83~120）**不再被压平**，改用 LC 自己的分带地面 83/89/107；`0% 落差` 只是因为那 12 个区块分成三簇、彼此不相邻（窗口只有 9 对），**不能**当作"城内无落差"的证据。修复前的同一格是"14 个区块全部 level 0（ground 71）"——也就是说，修复前是把这座山地城市整体削到 71（削 12~49 格）换来的"城内同高"。

**这是一条策划级冲突，需要决策（已列入 §6 与回复文档）**：D-T8 的"本格 ≥3/5 陆地才准入"对**海岸山地城市**（城市在山上、格内大部分是海/低地）会整格拒绝 ⇒ 该城市回到 LC 的分带落差。可选方向见 `docs/2026-09-26-核阅处理与回复.md` §5。
